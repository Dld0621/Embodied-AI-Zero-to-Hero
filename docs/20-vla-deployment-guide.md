# VLA 部署：让预测按正确时间变成正确动作

**更新与来源核查：2026-11-15。** 本页给出部署实验的方法与验收记录，替换旧版缺少日志支持的速度、显存、量化收益表和不可运行的集成草图。本轮没有执行 GPU 推理、导出引擎或机器人操作；下文算例是明确设定的教学数字。

先修：[VLA 系统课程](learning-core/09-vla-systems.md)、[动作表示](24-action-representation-and-tokenization.md)、[数据组织](21-vla-dataset-organization.md)。训练入口见 [SmolVLA 微调记录方法](28-smolvla-gpu-finetuning-runbook.md)。

## 1. 一个杯子任务为什么会部署失败？

模型输出 `[0.01, 0, 0]`，不能仅凭三个数字发给机器人。它可能表示“沿基座 x 轴移动 1 cm”，也可能是归一化值、速度或关节增量。与此同时，模型看到的杯子可能已经是 200 ms 前的位置。

部署需要同时回答两个问题：**这条动作是什么意思，以及现在执行它是否仍然合适？**

```text
相机曝光、状态读取
       ↓ 记录采集时间与标定版本
预处理 → 模型预测 → 解码与反归一化
       ↓ 校验动作合同、序号与观测年龄
执行队列 → 机器人控制器 → 实际状态与接触反馈
       └──────────重新观测──────────┘
```

VLA 的输出只是控制系统的一个输入。状态估计、执行器控制、接触判断和停止处理需要各自明确的实现与测量。

## 2. 先写动作合同，再选择加速方案

| 必须记录的字段 | 杯子任务的教学示例 | 检查方法 |
| --- | --- | --- |
| checkpoint、代码与处理器版本 | 固定权重 revision、代码 commit、processor 配置 | 重载后输出一致性 |
| 动作通道及顺序 | `dx, dy, dz, drx, dry, drz, gripper` | 单通道小幅测试 |
| 语义 | 末端增量；夹爪为绝对开合命令 | 对照训练标签与控制器 |
| 单位与坐标系 | m、rad；平移在基座系 | 标定与方向测试 |
| 旋转约定 | 本例采用基座系旋转向量增量，按约定次序合成 | 已知姿态往返 |
| 归一化 | 训练集统计量及逆变换、mask | 物理动作往返误差 |
| 时间 | 动作采样间隔、动作块长度、执行前缀 | 实际时间戳与队列日志 |
| 生效条件 | 动作年龄、限位、状态有效性 | 注入过期/缺失输入 |

这张表描述一个具体实现，不是所有 VLA 的公共动作空间。相同的七维向量可以有完全不同的意义。

原始 OpenVLA 的官方路径使用 `predict_action(..., unnorm_key=...)`，不能用普通文本 `generate()` 的耗时冒充已解码动作延迟。选择哪个 `unnorm_key` 由训练数据及权重决定；它不会自动把末端动作转换成关节位置。参见 [OpenVLA 官方实现](https://github.com/openvla/openvla)。

## 3. 三个“频率”必须分开

- **传感器频率**：相机与状态传感器多久产生一次观测。
- **策略更新频率**：多久完成一次新的动作预测。
- **动作命令频率**：策略动作按什么间隔发送给控制器；电机内部伺服可以采用另一频率。

动作块有 `H` 个动作，但每次只执行前 `K` 个，然后根据新观测重算。若动作采样间隔为 `dt`，执行前缀覆盖 `K × dt` 秒。增大 `K` 可以摊薄推理开销，同时增加重新观测前的执行时间。

$$
\begin{aligned}
T_{\mathrm{prefix}} &= K\,\Delta t,\\
T_{\mathrm{chunk}} &= H\,\Delta t.
\end{aligned}
$$

**教学算例：** 动作采样间隔 20 ms，预测 50 步，执行前 10 步；预测覆盖 1 s，执行前缀覆盖 200 ms。若一次推理需要 120 ms，同步系统在执行完前缀后等待推理，就可能产生 120 ms 的停顿。低层控制器在等待期做什么，需要另行指定。块内按 50 Hz 发送命令，不表示每秒完成 50 次模型生成，也不定义电机内部伺服频率。

不存在对所有任务通用的“低于 100 ms 就稳定”规则。稳定性与闭环动力学、增益、观测延迟、控制语义及接触有关；模型吞吐量不能替代这些验证。

## 4. 同步、异步与 RTC 分别解决什么？

| 方式 | 工作过程 | 必须检查的风险 |
| --- | --- | --- |
| 同步分块 | 执行前缀 → 获取观测 → 推理 → 执行 | 块间停顿、等待时的控制状态 |
| 异步预测 | 执行旧动作时生成新动作 | 旧观测、队列覆盖、切换不连续 |
| 实时分块 RTC | 生成时对已经承诺执行的动作进行条件约束 | 延迟估计、时间索引、可用的生成模型接口 |

```text
时间 →      0        1        2        3        4
执行线程    [旧块动作………………][切换后执行新块…………]
预测线程        [采样观测 → 预测新块…………]
                    ↑这段时间里旧块继续执行
```

异步只是并行调度方式。把新数组覆盖旧数组并不自动得到连续动作。原始 [RTC 论文](https://arxiv.org/abs/2506.07339)针对扩散/流策略，在生成下一块时约束已经承诺的前缀；[作者说明及后续工作入口](https://www.pi.website/research/real_time_chunking)区分推理时版本与后续训练时条件化版本。它们都不等同于简单插值，也不为任意回归头提供自动正确的适配。

## 5. 用同一条时间轴测延迟

至少记录以下事件，并明确使用同一台机器的单调时钟还是经过校准的跨机器时钟：

| 事件 | 建议字段 | 作用 |
| --- | --- | --- |
| 相机采集与可读 | `capture_time`, `receive_time` | 区分曝光、传输与排队 |
| 预处理起止 | `preprocess_start/end` | 图像解码、缩放、tokenization |
| 模型起止 | `inference_start/end` | 包含实际动作头/采样步骤 |
| 解码结束 | `decode_end` | 逆归一化、格式转换 |
| 指令生效 | `apply_time` | 包含队列、网络与控制器 |
| 反馈读取 | `feedback_time` | 记录实际运动与跟踪误差 |

$$
\begin{aligned}
T_{\mathrm{infer}} &= t_{\mathrm{end}}-t_{\mathrm{start}},\\
A_{\mathrm{obs}} &= t_{\mathrm{apply}}-t_{\mathrm{capture}}.
\end{aligned}
$$

`A_obs` 是**观测年龄**：动作真正应用时，模型所用图像已经过去多久。异步系统即使模型计算很快，排队仍可能让这个值很大。

报告 warm-up 次数、样本数、p50、p95、最大值、峰值显存、漏截止次数、队列长度与动作年龄。先预注册截止和年龄阈值，再报告超限率。分位数只是测量摘要，不保证未来调用不超时。

GPU 调用可能异步返回。测整条调用路径时，需要按所用后端完成同步；CUDA events 测得的设备时间与包含 CPU、相机、网络的端到端时间应分列。参考 [PyTorch CUDA 同步接口](https://docs.pytorch.org/docs/stable/generated/torch.cuda.synchronize.html)与 [NVIDIA 性能测量工作流](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html)。

## 6. 优化顺序：每次只改一个因素

| 候选改动 | 可能减少什么 | 重新验证什么 |
| --- | --- | --- |
| 相机数量/分辨率 | 传输、视觉 token 与编码成本 | 手指、接触区域是否仍可见 |
| BF16/FP16 或量化 | 权重/激活内存与部分算子成本 | 算子支持、动作误差与闭环任务 |
| 减少 flow/扩散采样步骤 | 动作头计算 | 分布质量、接触动作与成功率 |
| 连续并行动作块 | 串行 token 解码 | 训练目标及 checkpoint 是否匹配 |
| 编译或 TensorRT | Python 开销、算子执行 | 支持的 shape、控制分支、数值偏差 |
| 推理与执行分离 | 阻塞与设备利用率 | 过期动作、切换和队列语义 |
| 缓存不变条件 | 重复编码 | 缓存是否随图像/指令变化正确失效 |

先保留一个功能正确的基线，再固定相同输入、随机种子与评测任务做对照。减少动作维度、换数据集或缩短任务后得到的速度，不能直接归为某个加速器的收益。

不要把通用语言模型的 AWQ/GPTQ 脚本直接应用到任意 VLA 包装器。视觉塔、主干、动作专家和自定义算子分别需要支持；INT4 权重内存缩小也不等于端到端延迟按同一比例下降。导出成功之后仍需检查动作输出、处理器、逆变换及完整闭环。

## 7. 错误处理必须区分动作语义

**绝对位置的全零向量可能是“移动到零位”，不是停止。** 速度零、保持当前目标位置、减速停止、断开驱动具有不同含义，需要由机器人控制模式决定。

最小部署状态机应区分 `READY → RUNNING → STOPPING → STOPPED/FAULT`。发生过期观测、无穷/NaN、接口超时或人工停止时，记录触发原因、最后一次有效状态、已发送与已撤销的队列项，并调用该控制器验证过的停止路径。重启后重新同步时间和状态，不能继续播放故障前遗留动作。

关节限位、速度、加速度、碰撞和接触条件需组合检查，不能因为裁剪了一个维度就提前返回而跳过其余检查。限幅只处理所定义的约束，不证明抓持稳定或碰撞不可发生。

本仓库执行适配器与过滤器仍有独立审查项；本页重写不等于修复执行源码。接线前应对照 [F002/F003 及后续状态](reviews/content-audit-handoff.md)。

## 8. 灵巧手部署还需加哪一层？

VLA 选择“拿起杯子”后，还要将手指关节、腕部、物体状态与接触反馈接入控制回路。需要记录：关节顺序与耦合、腕手坐标变换、触觉校准、接触建立/丢失、跟踪误差、执行饱和与滑移判断。

几何重定向损失很小，仍可能因为摩擦不足、接触位置或动态执行失败。残差必须声明作用对象：目标关节、轨迹、力或动作块不能混用。参见 [接触与残差课程](learning-core/08-contact-retargeting.md)。

## 9. 交付一份可以复核的部署报告

1. 固定 checkpoint、软件环境、处理器、数据统计量与机器人控制合同。
2. 在固定观测集上保存原始输出、解码动作与参考输出差异。
3. 测量相同调用路径的延迟分布、观测年龄、峰值显存及截止超限。
4. 在留出的场景运行闭环评估，逐 episode 保存成功、失败、干预和停止原因。
5. 对灵巧操作分别报告接触、抓起、搬运、放置、释放与稳定保持；附连续轨迹及视频对应关系。

**实践验收：** 比较同步与一种异步实现，先画出预期时间轴，再保存实际事件日志。只有当动作语义一致、结果可重算且任务质量也经过对照时，才能把优化写进结果表。
